# 「サクいこ」Ver.0.1 仕様書(統合版)

## 1. コンセプト

**ジャンルを選ぶだけで、近場の「今なら比較的入りやすそうな店」を3秒で決めてくれるWebアプリ。**

大量の店舗情報を比較するのではなく、「今どこに行くか決める」ことに特化する。

最適解を教えるアプリではなく、**悪くなさそうな選択肢の中から、背中を押して決めてくれるアプリ**という位置づけ。

## 2. アプリ名

**サクいこ**(「サクッと行こう」の意)

候補だった「イマイコ」は、同名の出会い系アプリが既に存在し悪評があったため不採用とした。

## 3. 基本方針

- 完全無料(個人開発の範囲で運用)
- ログインなし・会員登録なし・DBなし
- localStorageは使用しない(セッション内のJS変数のみで完結)
- 位置情報は検索のためだけに一時利用し、保存しない
- 行動履歴・訪問履歴・混雑実績の記録機能は実装しない(プライバシー上の理由。将来要望があればON/OFF・確認・削除可能な形で再検討)
- Ver.0.1の成功条件は予測精度の高さではなく、**「短時間で行く店を決められたか」**

## 4. 技術構成

```
ブラウザ(GitHub Pages: https://ai-shisakusho.github.io/saku-iko/)
   ↓ genre / lat / lon のみ送信
Cloudflare Worker「sakuiko-proxy」(sakuiko-proxy.ai-shisakusho.workers.dev)
   ↓ Geoapify URLを組み立てて中継
Geoapify Places API
```

- フロント:HTML / CSS / JavaScript、Geolocation API
- 店舗データ:Geoapify Places API(データソースはOpenStreetMap)
- APIキー保護:Cloudflare Workers(無料枠、カード不要)でプロキシを挟み、GeoapifyキーはCloudflareのSecretとして保管。コード上にキーは一切出さない
- 公開:GitHub Pages

### 4.1 技術選定の経緯(Overpass API→Geoapifyへの移行)

当初はOpenStreetMap + Overpass API(APIキー不要)での構成を検討したが、実機検証で不採用と判断した。

**検証結果(東京・新宿・渋谷×3ジャンル×各3回=27回、node+bbox・500m・逐次実行)**

| 指標 | Overpass(v6) | Worker(Geoapify) |
|---|---|---|
| 成功率 | 56% | 100% |
| 平均時間 | 4.79秒 | 1.15秒 |
| 中央値 | 4.85秒 | 1.15秒 |
| 最大時間 | 10.67秒 | 1.61秒 |
| 3秒以内の割合 | 33% | 100% |

事前に決めた採用基準(成功率90%以上・3秒以内が大半)をOverpassは大きく下回ったため不採用。Geoapify + Cloudflare Workerへ移行し、同条件のテストで基準を大きく上回ったため採用を確定した。

### 4.2 APIキー保護の設計

- ブラウザからはGeoapifyを直接呼ばず、Cloudflare Workerを経由する
- Workerが受け付けるパラメータは `lat` / `lon` / `genre` / (任意)`radius` のみ
- Worker側でgenreを固定のGeoapifyカテゴリに変換し、radius・limit(最大20)・lat/lonの範囲チェックを行った上でWorker自身がGeoapify URLを組み立てる(ブラウザからのクエリをそのまま転送しない)
- `Origin`ヘッダーで、GitHub Pages(`https://ai-shisakusho.github.io`)以外からのアクセスを拒否
- `Cache-Control: no-store`、独自ログは残さない
- 完全な防御ではない(Originヘッダーは偽装され得る)が、Geoapify無料枠の上限(3,000 credits/日)が実質的な歯止めになる

## 6. ジャンル設計

OSM日本語Wikiの慣習(`pub`=居酒屋・飲食主目的、`bar`=スナック・バー等飲酒主目的で風俗性のある店を含みうる)に基づき、以下に確定した。

| アプリ表示 | Geoapifyカテゴリ |
|---|---|
| ☕ カフェ | `catering.cafe` |
| 🍺 居酒屋 | `catering.pub` |
| 🍜 ごはん | `catering.restaurant` + `catering.fast_food` + `catering.food_court` |
| 🎲 おまかせ | 上記3ジャンルから検索実行時にランダムで1つ選択 |

**`catering.bar`はVer.0.1では検索対象から完全に除外する。**

理由:キーワードでの後付けフィルタ(「スナック」「ガールズバー」等を店名で除外)は誤除外・見逃しの両方が発生しやすく曖昧。カテゴリの選び方自体で構造的に回避する方が確実。特に「おまかせ」でスナック・ガールズバー系が突然提示される事態は、「おまかせしていない」体験になるため避ける。精度(全店舗網羅)より「変な店を出しにくいこと」を優先する。

## 7. 店舗検索ロジック

### 7.1 検索範囲

初期半径1km、候補が3件未満の場合のみ2kmまで拡大する。

### 7.2 「空いてそう度」の予測

リアルタイム混雑情報は使わず、以下から独自に予測する。

- 曜日(平日/土日、金土か)
- 現在時刻
- 店舗ジャンル

結果は3段階。

- 🟢 空いてそう
- 🟡 普通そう
- 🔴 混んでそう

判定結果には「平日17時台は比較的入りやすい時間帯です」のような予測理由の一言を添える。「現在空いています」ではなく「空いてそう」という表現を用い、実測ではなく予測であることを明示する。

「おまかせ」では、Geoapifyから返るカテゴリタグをもとに実ジャンル(カフェ/居酒屋/ごはん)を判定してから、同じロジックで予測する。

### 7.3 並び順とランダム性

空いてそう度×距離でスコアリングし、上位5件に絞る。そこから**重み付きランダム**で1件を「今ならここ」として提示する。

| 順位 | 選出確率 |
|---|---|
| 1位 | 35% |
| 2位 | 25% |
| 3位 | 20% |
| 4位 | 12% |
| 5位 | 8% |

完全固定(常に1位のみ表示)ではなく、かつ「遠くて混んでそうな店がランダムで出る」ことも避ける、両者のバランスを取った設計。

**「↻ 別の候補」ボタン**:押すとAPIを再取得せず、既に取得済みの上位5件から重み付きランダムで選び直す。一度出した店はそのセッション(画面を開いている間)だけ除外され、全部出し切ったら一巡してリセットする。localStorageは使わずJavaScriptのメモリ上だけで完結する。

**「✕ これは違う」ボタン**:「今ならここ」と「ほかの候補」の各店に設置。押すとその店を今回の検索結果から完全に除外する(APIの再取得はしない)。「今ならここ」で押した場合は残りの候補から自動で代わりを選び直し、「ほかの候補」で押した場合は表示中の「今ならここ」を維持したまま一覧だけ更新する。除外は今回の検索セッション内のみ有効で、画面を閉じる・リロードすれば忘れる(保存はしない)。

## 8. 店舗詳細情報の役割分担

**サクいこで行うこと**

- 近場の候補を探す
- 空いてそう度を予測
- 距離を計算
- おすすめ順に並べる
- 「今ならここ」を提示

**Googleマップに任せること**

- ★評価・口コミ・写真・メニュー
- 最新の営業時間・営業状況
- 経路案内

店舗ごとに「Googleマップで営業状況を確認して行く」ボタンを設置する(後述の閉店店舗対策も兼ねる)。

## 9. 閉店店舗対応方針

Geoapify(データソースはOSM)は閉店情報の更新が追いつかず、実際には閉店済みの店舗が候補に出ることがある(実機確認例:麺屋てつ蔵 東武練馬店、升屋 東武練馬店)。100%の検出は無料MVPの範囲では不可能という前提のもと、以下の3段階で対応する。

1. **明示的な閉店タグがある店舗をWorker側で除外**:Geoapifyレスポンスの`datasource.raw`に`disused:*` / `abandoned:*` / `closed:*` / `was:*` / `former:*` / `removed:*` / `demolished:*`のいずれかのキー、または過去日付の`end_date`があれば除外する
2. **Googleマップボタンで最終確認を促す**:ボタン文言を「Googleマップで営業状況を確認して行く」にする
3. **注意書きの表示**:「店舗情報が古い場合があります」を結果画面に小さく表示する

**あえてやらないこと**:`check_date`や`survey:date`が古いという理由だけでの除外は行わない。実際には営業中でも単にOSM上で最近確認されていないだけの店舗まで消してしまうリスクがあるため。

**残る限界**:OSM側がそもそも閉店を認識していない(誰も更新していない)ケースは、タグベースの除外では検出できない。根本解決には Google Places APIの`business_status`など別の最新データソースとの照合が必要だが、コスト増・実装複雑化を伴うため、無料MVPの範囲を超えるとして現時点では見送り、将来的な検討事項として保留する。

## 10. プライバシー方針

- 現在地は店舗検索のためCloudflare Worker・Geoapifyへ送信されるが、アプリ側では保存しない
- 送信前に緯度経度を小数4桁程度に丸める(精度への影響はほぼないが、不要に細かい位置情報は送らない)
- 検索履歴・訪問履歴・お気に入り・「実際どうだった」等の記録は行わない
- localStorageは使用しない

## 11. Ver.0.1で入れないもの

- ログイン・会員登録・DB
- Google Places API(店舗検索本体としては不使用。閉店判定の将来的な精度向上策としてのみ検討対象)
- 行動履歴・訪問履歴の保存
- お気に入り
- AI推薦・予約機能・ランキング
- 詳細検索・ソート機能
- `catering.bar`(スナック・ガールズバー等を含みうるジャンル)
